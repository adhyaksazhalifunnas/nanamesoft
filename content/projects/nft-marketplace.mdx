problem: >
  The company wanted to know whether Web3 was something its front-end team could
  build on, and nobody there had done it. The honest answer needed a working
  system rather than a report: minting a token, listing it, and buying it are
  each easy to describe and each behave unlike anything in a normal web stack —
  the write is slow, it costs the user real money, and it can fail after the user
  has already confirmed it. I was given the question and built the whole thing
  from nothing to answer it.

constraints:
  - "Four months, alongside the rest of an internship, with nobody at the company who had built on-chain before to ask."
  - "Every state-changing action costs the user gas, so the usual web habit of writing on every interaction is not available."
  - "A blockchain write is asynchronous and can fail after the user has already approved it in their wallet — the interface has to survive that."
  - "Contract code cannot be patched after deployment the way a web deploy can, so mistakes are permanent in a way front-end mistakes are not."

decisions:
  - decision: "What to build the contracts and their tooling on"
    chosen: "OpenZeppelin's ERC-721 implementation, developed and tested with the Hardhat toolbox"
    alternatives:
      - "Writing the ERC-721 implementation from scratch to understand it fully"
      - "Truffle and Ganache, the older standard toolchain"
      - "Working entirely in Remix in the browser"
    rationale: >
      A token standard is exactly the code you should not write yourself: the
      OpenZeppelin implementation is audited and widely deployed, and a subtle
      mistake in transfer or approval logic is permanent once deployed. Hardhat
      gave me a local chain, Chai tests, TypeChain types shared with the front
      end, a gas reporter and Etherscan verification from one config, which
      mattered when I was the only person on the project.
    tradeoff: >
      Inheriting a standard implementation means inheriting its assumptions and
      its bytecode size, and I understand the parts I overrode better than the
      parts I did not. Hardhat also costs more setup than opening Remix — which
      only pays off because the tests and the gas measurements paid it back.
  - decision: "What to build the front end on"
    chosen: "Next.js talking to the contracts through ethers.js, with the integration kept in its own repository"
    alternatives:
      - "A plain React single-page app"
      - "web3.js instead of ethers.js"
    rationale: >
      Splitting contracts, interface and the integration layer into three
      repositories kept the boundary explicit: the interface never reaches for a
      contract directly, it goes through one layer that owns the ABI, the
      addresses and the TypeChain types. Ethers pairs with that cleanly, and it
      is what the Hardhat toolbox already uses, so the tests and the app spoke
      the same library.
    tradeoff: >
      Three repositories for one product is real overhead for one person — a
      contract change means a coordinated update in two other places. It also
      means no page showing chain data can be statically rendered, because the
      data only exists once a wallet is connected.
